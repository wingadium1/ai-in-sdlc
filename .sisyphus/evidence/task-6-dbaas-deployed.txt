2. DBaaS ARCHITECTURE OPTIONS DOCUMENTED
================================================================================

Three architecture patterns were evaluated against the VMware DSM baseline:

Pattern-1: Reuse on RHOSO/OpenStack (SBKK Self-Built)
  - Infrastructure: Shared RHOSO 18 / upstream OpenStack layer
  - DBaaS Engine: VM-based reuse model (customer-managed images + Ansible)
  - Image Ownership: Customer (SBKK)
  - Admin Console: Must build (Spring Boot BFF + frontend)
  - HA Model: Existing SBKK model (pgpool / Patroni)
  - Operational Burden: HIGH
  - Source: deployment/comparison/dbaas/patterns-comparison/01-architecture-comparison.md

Pattern-2A: Production-Ready on RHOSO/OpenStack
  - Infrastructure: Same shared OpenStack layer as Pattern-1
  - DBaaS Engine: VM-based production-ready target design
  - Image Ownership: To be standardized by target design
  - Admin Console: Must build (stronger service UI/BFF than P1)
  - HA Model: Production-ready VM HA (to be selected)
  - Key Differentiator: Custom DBaaS controller (Trove ruled out; TBD)
  - Operational Burden: MEDIUM
  - Source: deployment/comparison/dbaas/patterns-comparison/01-architecture-comparison.md

Pattern-2B: FPT Cloud (Managed Service) — RECOMMENDED
  - Infrastructure: FPT Smart Cloud (managed OpenStack + FPT RDS)
  - DBaaS Engine: FPT Cloud RDS (managed service)
  - Image Ownership: Provider (FPT-managed)
  - Admin Console: Built-in (FPT portal) — no development required
  - HA Model: Managed HA/failover by FPT
  - Operational Burden: LOW
  - Source: deployment/comparison/dbaas/patterns-comparison/01-architecture-comparison.md

VMware DSM Baseline
  - Current environment: VMware Data Services Manager on vSphere
  - Engine Support: PostgreSQL, MySQL only
  - Cost Driver: Broadcom acquisition raised licensing 200–400%
  - Source: deployment/comparison/dbaas/README.md

4.1 AWS RHOSO Validation Environment (PoC — COMPLETED)
------------------------------------------------------
Architecture:
  - OCP Cluster (RHOCP 4.18) with 3 control + 3 worker nodes
  - RHOSO 18.0 operators (Nova, Neutron, Glance, Keystone, Placement, OVN)
  - 3 bare-metal EC2 compute nodes (c5d.metal: 96 vCPU, 192GB RAM, 4xNVMe)
  - RAID5 on each compute node (3 active + 1 hot spare = ~1.8 TB usable)
  - Monitoring: Prometheus + Alertmanager + Grafana on m5.large
  - Backup: AWS EFS (NFS-compatible) for pgBackRest
  - Bastion: t3.medium with public EIP

Network Topology (7 subnets):
  - ocp-public:     10.0.0.0/24  (Bastion EIP, Monitoring)
  - ocp-private:    10.0.1.0/24  (OCP internal traffic)
  - ctlplane:       10.0.10.0/24 (EDPM Ansible → compute SSH)
  - internalapi:    10.0.11.0/24 (OpenStack API endpoints)
  - tenant:         10.0.12.0/24 (OVN tunnel, PG replication)
  - backup/storage: 10.0.13.0/24 (pgBackRest → AWS EFS)
  - provider:       10.0.14.0/24 (DB VMs, VIP 10.0.14.210)

Patroni HA Cluster Stack:
  - PostgreSQL 16
  - Patroni (latest pip release)
  - etcd 3.5.17 (3-member cluster for quorum)
  - VIP management via Patroni callback script (patroni-vip.sh)
  - Cluster scope: pg-cluster

Key Configuration Requirements:
  - etcd MUST have --enable-v2=true (python-etcd library requirement)
  - eth0 (ctlplane) must NEVER be enslaved into OVS bridge (AWS constraint)
  - Dedicated eth1 on separate subnet used for br-ex instead

6. DEPLOYMENT STEPS SUMMARY (What WOULD Be Followed)
================================================================================

Based on the documented procedures, the following deployment steps would be
followed for a production DBaaS deployment on RHOSO:

Phase 1: Infrastructure Preparation
  1. Provision bare-metal compute nodes (3+ nodes with NVMe drives)
  2. Configure RAID5 on each node (3 active + 1 hot spare)
  3. Deploy OpenShift 4.18 cluster (3 control + 3 worker nodes)
  4. Deploy RHOSO 18.0 operators via OpenShift
  5. Configure EDPM Ansible for compute node management
  6. Set up 7-subnet network topology (public, private, ctlplane,
     internalapi, tenant, backup, provider)
  7. Deploy monitoring stack (Prometheus, Alertmanager, Grafana)
  8. Configure backup target (NFS or S3-compatible storage)

Phase 2: DBaaS Controller Decision
  1. Trove has been ruled out — do not use
  2. For Pattern-2A: Design and build custom DBaaS controller (future phase)
  3. For Pattern-1: Use Ansible directly for provisioning
  4. For Pattern-2B: Consume FPT Cloud RDS via portal/API

Phase 3: PostgreSQL HA Cluster Deployment
  1. Deploy 3-member etcd cluster (enable v2 API for python-etcd)
  2. Install PostgreSQL 16 on all DB nodes
  3. Install and configure Patroni on all DB nodes
  4. Configure streaming replication (synchronous + asynchronous hybrid)
  5. Deploy VIP callback script for Neutron allowed-address-pairs
  6. Configure pgBackRest for backup (full + incremental + WAL archive)
  7. Set up monitoring exporters (node_exporter, pg_exporter)
  8. Configure Alertmanager rules for WAL lag, disk usage, CPU, failover

Phase 4: Validation
  1. Execute V1–V37 validation items per TEST-PLAN.md
  2. Collect evidence (screenshots, command outputs)
  3. Verify all T1/MUST items pass
  4. Document findings and mitigations
