1. PRIMARY RHOSO DEPLOYMENT DOCUMENTATION
--------------------------------------------------------------------------------
File: deployment/rhosp/README.md (214 lines, status: stable, dated 2026-03-19)

1.1 Architecture Overview
- Product: Red Hat OpenStack Services on OpenShift (RHOSO), aka RHOSP 18
- OpenStack Version: 2024.2 (Dalmatian)
- Control Plane: Podified architecture running on Red Hat OpenShift Container
  Platform (RHOCP) 4.18+
- Data Plane: Bare-metal RHEL 9 compute nodes (Libvirt + OVS/OVN agents)
- Orchestration: Kubernetes-native Operator framework (replaces TripleO/Director)

1.2 Control Plane Components (running as pods on OpenShift)
- Keystone (Identity)
- Nova (Compute orchestration)
- Neutron (Networking)
- Cinder (Block storage)
- Glance (Image service)
- MariaDB/Galera (Database — managed by Galera Operator)
- RabbitMQ (Messaging — managed by RabbitMQ Cluster Operator)
- OVN (Open Virtual Network — exclusive network backend)

1.3 Key Custom Resources (CRDs)
- OpenStackControlPlane (top-level CR defining entire control plane state)
- KeystoneAPI (service-specific CR for Identity)
- OpenStackDataPlaneNodeSet (defines compute node configuration)
- NodeNetworkConfigurationPolicy (NNCP) via nmstate operator

1.4 High Availability
- Pod HA: OpenShift Scheduler + ReplicaSets
- Database HA: Galera Operator (MariaDB cluster)
- Messaging HA: RabbitMQ Cluster Operator
- API Routing: OpenShift Services/Routes (replaces HAProxy/Keepalived)

1.5 Storage Integration
- Preferred backend: Red Hat Ceph Storage 8 (RHCS 8)
- Cinder/Glance/Nova use Ceph RBD
- Manila uses CephFS
- Secrets stored as OpenShift Secrets

1.6 Deployment Workflow (6 steps)
  1. Install OpenShift (RHOCP 4.18+)
  2. Install Operators via OLM
  3. Configure Networking (NNCPs)
  4. Deploy Control Plane (OpenStackControlPlane CR)
  5. Provision Data Plane (OpenStackDataPlaneNodeSet CR)
  6. Verification (service connectivity, VM spawning)

1.7 Prerequisites
- RHOCP 4.18+ (mandatory)
- Valid Red Hat subscriptions (OpenShift, OpenStack, Ceph)
- Bare-metal servers for Compute nodes (RHEL 9 support)
- Minimum 3 Master + 3 Worker nodes for OpenShift control plane

1.8 Limitations
- Requires expertise in both Kubernetes/OpenShift and OpenStack
- Full OpenShift cluster overhead just for OpenStack control plane
- Customization limited to CRD schema exposure
- Hard dependency on OpenShift lifecycle and networking model

3. OPERATOR-BASED DEPLOYMENT MODEL
--------------------------------------------------------------------------------
- Each OpenStack service has its own Operator (e.g., Keystone Operator, Nova
  Operator, OpenStackDataPlane Operator)
- Operators watch CRDs and reconcile actual pod state to match desired spec
- OLM (Operator Lifecycle Manager) handles installation and updates
- Upgrades are declarative:
  * Minor: Updating Operator version triggers rolling pod updates
  * Major: Updating OpenStackControlPlane spec triggers orchestrated DB schema
    and service updates
  * Data Plane: Updating NodeSet CR triggers Ansible playbooks for RPM updates
- GitOps native: Entire deployment defined by YAML CRs (ArgoCD/ACM compatible)
- Monitoring: OpenShift monitoring stack (Prometheus/Grafana) via ServiceMonitors
- Logging: OpenShift logging stack (Vector/Loki or Elasticsearch/Fluentd)
- Tooling: `oc` commands and OpenStack CLI in toolset pods

      ansibleSSHPrivateKeySecret: dataplane-ansible-ssh-priv-key
      managementNetwork: ctlplane

7. NETWORK CONFIGURATION
--------------------------------------------------------------------------------
- Backend: OVN (Open Virtual Network) — exclusive
- Declarative networking: NodeNetworkConfigurationPolicy (NNCP) via nmstate
- Six primary network planes:
  1. ctlplane: Management and provisioning
  2. internalapi: Internal service communication
  3. tenant: Overlay traffic for VM instances
  4. storage: Traffic to/from storage backends
  5. storagemgmt: Backend storage replication and management
  6. external: External connectivity and Floating IPs
- LoadBalancer: MetalLB within OpenShift for OpenStack API endpoints
- Physical lab mapping (from physical-rhoso-install.md):
  * ctlplane -> VLAN 10
  * internalapi -> VLAN 11
  * tenant -> VLAN 12
  * storage/backup -> VLAN 13
  * provider -> VLAN 14
